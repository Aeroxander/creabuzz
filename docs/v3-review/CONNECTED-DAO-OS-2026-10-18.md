# Connected project overview and social progress — 18 October 2026

> **History (noted 2026-10-23).** A progress note of 2026-10-18. The navigation it describes was renamed since (Workspaces became Communities, D92); for what is built now see [STATUS-2026-10-22.md](STATUS-2026-10-22.md).

The user selected Project first and asked me to work on the unfinished social and DAO OS features. This increment connects the existing project, relay work, agent and onchain claim surfaces. It does not replace the relay architecture or add a trading dependency to coordination features.

## What is implemented

- Main navigation is Home, Discover, Workspaces and Portfolio. Existing URLs remain valid. Discover links to Launches and Markets; Home links to People & posts. The existing Communities route remains directly accessible under Workspaces.
- Home puts personal actions ahead of onboarding and adds a project-progress feed for followed projects and the viewer's own team projects, with an All projects view.
- The feed merges existing signed team-post updates and older launch-update records. A stranger's update label does not confer team status. Outside contributor evidence does not become a team report just by naming a claim. Team-authored evidence is labeled as a submission, not approval or payment; claim-evidence review remains in Work. Cards show authors, dates, explicit artifact links, reactions, project discussion and a copyable update link.
- Project pages show team-recorded work, its owner or agent, review needs, milestone context and direct task links. Only rows signed by the current named team are merged into this overview: project citations, teammate assignees and public channel membership cannot confer endorsement. Foreign rows cannot overwrite an official task’s title, links or status. Other participants’ updates remain available in the existing community Work board; a team member must record them before they appear in this summary. This is a deliberate summary policy, not new relay-level task permissions. DAO overviews keep their action queue and treasury figures above the delivery detail and compact progress feed. Completed projects have a shorter decorative header; the full milestone rules are expandable.
- Reading history is browser-local, bounded, and scoped by relay, account and author-qualified project coordinate. A project visit records only the reports rendered after successful reads; its previous-visit baseline remains fixed while the person reads. A late-arriving report is not silently marked read by its older timestamp. Home offers explicit marking of the shown updates in one atomic storage write across projects and project pages expose more reports on demand. The digest covers loaded update reports, not every treasury, task or chain-state transition.
- Task detail can save a project coordinate, an output URL and a reference to an existing onchain claim. It verifies the project's network before reading claims, scopes that read by endpoint/network, and reads the claim status rather than inferring it from task completion. The claim link opens and focuses the matching claim in the Work tab. A failed save leaves the draft available for retry. The overview attributes a claim reference to the team signer who last recorded it and says approval/payment are not implied; task detail shows the claim’s actual contributor and status.
- Delivery references persist through older agent status rows. Within the retained task-row history, editing a completed task’s links preserves its completion identity for contribution credit and its recorded approver. This does not establish an unlimited-history once-only credit guarantee. These are references and provenance, not financial authorization.
- The new People & agents project tab joins project tasks with the founder-managed community helper seats, heartbeat status, responsible seat author, outputs, review needs, and recorded budget/approval limits. It links to the existing role, budget, emergency-stop and tab-helper controls. This view uses only founder-signed budget records, and Reload records retries the failed sources without reloading the document. Role/roster retry is fenced against retired requests; budget queries are scoped by relay and account. Community seats are explicitly described as community-wide; an assignment or announcement never proves wallet authority. Recorded limits carry the existing enforcement labels, and their display is not a live spending or allowance balance. DAO-wide agent costs remain unavailable; browser-helper usage is not relabeled as a project total.
- The review's claim-expiry finding is fixed: a review item includes its deadline, outranks a later vote, and explains that anyone can close an unanswered claim after expiry and return the stake/reserved payment. At the exact deadline the contract still does not allow expiry; the post-deadline wording follows that boundary.

New task-link writes carry the project coordinate in an `a` tag while retaining their `h` privacy scope. The project-work read is bounded to eight linked channels and 64 team signers, with a project-tag query and a 200-row team-only discovery fallback for legacy links. For up to 100 discovered tasks it reads known-id history (at most 1,000 rows per scope, matching the relay page cap), so an older writer’s status update or removal without an `a` tag still wins. Live subscriptions are project/channel/known-task scoped, never relay-wide. Legacy links outside the bounded discovery window still need republishing to be indexed; the view reports full windows instead of claiming complete history. Failed channels and truncated histories remain visible. Server authorization still controls all private-channel reads. Private task titles, agent traces and outputs are not automatically published into the social feed. Founder update copy asks people to include only artifacts they intend to share.

The launch form now illustrates the default 20/30/50 schedule before launch: earliest unlocks on days 7, 51 and 102 after the first report, and eligibility to reclaim the final bond on day 132. It explains the assumptions (no objections/retries, immediate publication when allowed and explicit finalization), rather than promising those dates. The D60 decision-table formatting is fixed and D59’s pending-work list is marked as historical.

## Mechanisms and compatibility

No new HTTP endpoint, event kind, contract, token privilege or automatic payment path was added. Task links are an optional `delivery` object in the existing kind:44011 content:

```json
{
  "project": "37001:<project-author>:<project-id>",
  "output": "https://example.com/demo",
  "claim": { "id": "0x<claim-id>", "mandate": "0x<work-budget>" }
}
```

`output` and `claim` can be null; clearing `delivery` is explicit null. Old writers can omit it without erasing the most recent value. Output links accept only HTTP/HTTPS without embedded credentials. References cannot create a claim, approve it, award Shares or transfer funds. Saved links may outlive a later claim state; the status read and explicit Work-tab actions remain authoritative.

The frontend direction extends the original platform vision toward the user's DAO OS goal while retaining its core constraints: signed relay events, community isolation, human accountability and existing onchain authority. Social reactions and contribution credit remain separate from economic ownership and governance standing.
